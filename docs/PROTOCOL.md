# Studio ↔ bdld protocol

* **Schema**: `crates/bdl-protocol/proto/bdl/v1/bdl.proto` — the single
  source of truth. Rust code is generated at build time (`prost` + `protox`,
  no external `protoc`); Dart code is generated by `just proto` and checked
  in under `apps/studio/lib/protocol/gen/`; CI fails if it drifts.
* **Version**: `PROTOCOL_VERSION` (Rust) / `kClientProtocolVersion` (Dart),
  currently `0.3.0` (0.2 added the reactive statuses, causality/clock summary and simulation; 0.3 added clock/output/device edit ops and views, the output pass in `ProjectAnalysis`, `ListTargets` and `AnalyzeDeployment`). Equal `major` ⇒ compatible. The handshake reports both
  and a `compatible` flag; Studio refuses to proceed on a mismatch.
* **Transport** (v0.1): child-process stdio. Frame = 4-byte big-endian length
  + protobuf payload, 64 MiB cap. Stdout is the channel; bdld logs to stderr.
  Transport and protocol are separate: loopback TCP can be added without
  touching messages.

## Envelope

```
ClientMessage { request_id, oneof payload }   →
                                              ←  ServerMessage { Response { request_id, oneof } | Event { oneof } }
```

Exactly one `Response` per request. `Event`s are unsolicited and only sent
after `SubscribeProject`: `ProjectChanged` then `AnalysisReady` for every
committed revision.

## Requests (v0.1)

| Request | Response | Notes |
|---|---|---|
| Handshake | HandshakeResponse | versions, compatibility |
| OpenProject / InitProject | ProjectResponse | |
| SaveProject | ProjectResponse | `dirty` becomes false |
| CloseProject | Ack | |
| GetProject | ProjectResponse | |
| ApplyEdit { base_revision, EditOp } | EditApplied { projection, outcome } | refused with `edit.stale_revision` if the project moved on |
| Undo / Redo | EditApplied | new revision, no outcome |
| SetLayout | Ack | not a revision |
| SubscribeProject | Ack | then `ProjectChanged` events |
| RunAnalysis | AnalysisResponse { ProjectAnalysis } | analysis of the current snapshot, tagged with its revision |
| StartSimulation { inputs, schedule } | SimulationResponse | a run against the current revision; refused if not causal; dropped by any commit |
| StepSimulation { ticks } | SimulationResponse { samples, error? } | evaluates ticks; samples carry `DeclId`, active domains, values rendered in design terms |
| ResetSimulation | SimulationResponse | back to tick 0 |
| ListTargets | TargetsResponse { TargetView { id, name, resource_count }[] } | the board registry |
| AnalyzeDeployment { target_id } | DeploymentResponse { DeploymentAnalysis } | target-relative; computed afresh per request against the current revision, never cached with the project; `deploy.unknown_target` if the id is unknown |
| Shutdown | Ack | |

`EditOp` covers concepts, mappings, clock domains (`CreateClockDomain`,
`RenameClockDomain`, `DeleteClockDomain`, `SetMappingClock`), outputs
(`CreateOutput`, `RenameOutput`, `SetOutputAccepts`, `SetOutputClock`,
`SetOutputRequired`, `DeleteOutput`, `SetMappingDrive`) and devices
(`CreateDevice`, `RenameDevice`, `SetDeviceKind`, `SetDeviceOutput`,
`SetDevicePin`, `DeleteDevice`); `EditOutcome` reports `created_clock /
created_output / created_device`. Manual pins are deployment constraints
that travel with the device (`SetDevicePin { index, resource? }`) —
there is no separate "manual resource constraint" request.

`DeploymentAnalysis { revision, target, status: Feasible | Infeasible |
Incomplete, requirements[] (device, index, capability, fixed?, label),
assignment[] (device, index, resource), dead_end? { device, index, reason:
no_capable_resource | fixed_unavailable(resource) | blocked(candidates[]
{ resource, held_by }) , placed[] }, unbound_devices[],
unrealised_outputs[], diagnostics[] }` is structured for a Deploy page
(per output → device → requirement → resource, and the blocker), not a
string.

Planned (ROADMAP): RunSimulation, GenerateRust, Build, Flash, StartTelemetry.

## Errors

`Error { code, message, details_json }`. `code` is stable and
machine-readable (`edit.duplicate_concept_name`, `session.no_project`,
`protocol.invalid_edit`, …); `message` is designer-readable; `details_json`
carries the typed Rust error for the expert view.

## Projection

`ProjectProjection { revision, name, root_path, concepts[], mappings[],
layout, can_undo, can_redo, dirty, clocks[], outputs[], devices[] }` — a
read model for rendering, in deterministic order. `MappingView` carries
`clock_id?` and `drives_output_id?`; `OutputView { accepts, clock_id?,
required }`; `DeviceView { kind, output_id?, fixed_pins[], requirements[]
}` where `requirements` is the kind's requirement table (index, capability,
label) so a pin editor needs no hardware knowledge. `MappingView.state`
carries the paper's workspace state (`declared` / `defined`; the ladder
proper is in `ProjectAnalysis`).

`ProjectAnalysis` adds `outputs[] { id, state: undriven | driven |
ill_formed | conflict, driver?, claimants[] }`, `open_outputs[]` and
`output_complete`.

## Deltas

v0.1 sends the full projection after every commit. Incremental deltas are a
planned, non-breaking addition (a new `ProjectDelta` event); clients must
keep treating `ProjectChanged.project` as authoritative when present.
