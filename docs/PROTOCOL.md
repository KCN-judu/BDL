# Studio ↔ bdld protocol

* **Schema**: `crates/bdl-protocol/proto/bdl/v1/bdl.proto` — the single
  source of truth. Rust code is generated at build time (`prost` + `protox`,
  no external `protoc`); Dart code is generated by `just proto` and checked
  in under `apps/studio/lib/protocol/gen/`; CI fails if it drifts.
* **Version**: `PROTOCOL_VERSION` (Rust) / `kClientProtocolVersion` (Dart),
  currently `0.6.0` (0.2 added the reactive statuses, causality/clock summary and simulation; 0.3 added clock/output/device edit ops and views, the output pass in `ProjectAnalysis`, `ListTargets` and `AnalyzeDeployment`; 0.4 added the definition-draft requests: `AnalyzeDefinitionDraft`, `DiscardDefinitionDraft`, `CompleteDefinitionDraft`, `HoverDefinitionDraft`, then — additively, without a bump — `HoverEntity`, `ListSemanticActions`, `EntityRef` and `Layout.outputs`; 0.5 added the Deploy read model — `TargetView` chooser fields, `AnalyzeDeploymentRequest.revision`, and `DeploymentAnalysis` fields 10–15 — all additive; and the concept libraries: `ListConceptTemplates`, `InstantiateConceptTemplate`; 0.6 added behaviour systems — `InitSystemProject`, `GetSystem`, `ApplySystemEdit`, `RunSystemAnalysis`, `ProjectProjection.kind`, and the `reference` definition form — all additive). Equal `major` ⇒ compatible. The handshake reports both
  and a `compatible` flag; Studio refuses to proceed on a mismatch.
* **Transport** (v0.1): child-process stdio. Frame = 4-byte big-endian length
  + protobuf payload, 64 MiB cap. Stdout is the channel; bdld logs to stderr.
  Transport and protocol are separate: loopback TCP can be added without
  touching messages.

## Envelope

```
ClientMessage { request_id, oneof payload }   →
                                              ←  ServerMessage { Response { request_id, oneof } | Event { oneof } }
```

Exactly one `Response` per request. `Event`s are unsolicited and only sent
after `SubscribeProject`: `ProjectChanged` then `AnalysisReady` for every
committed revision.

## Requests

| Request | Response | Notes |
|---|---|---|
| Handshake | HandshakeResponse | versions, compatibility |
| OpenProject / InitProject | ProjectResponse | |
| SaveProject | ProjectResponse | `dirty` becomes false |
| CloseProject | Ack | |
| GetProject | ProjectResponse | |
| ApplyEdit { base_revision, EditOp } | EditApplied { projection, outcome } | refused with `edit.stale_revision` if the project moved on |
| Undo / Redo | EditApplied | new revision, no outcome |
| SetLayout { Layout { concepts[], mappings[], outputs[] } } | Ack | not a revision; positions keyed by stable id, outputs are canvas nodes too |
| SubscribeProject | Ack | then `ProjectChanged` events |
| RunAnalysis | AnalysisResponse { ProjectAnalysis } | analysis of the current snapshot, tagged with its revision |
| StartSimulation { inputs, schedule } | SimulationResponse | a run against the current revision; refused if not causal; dropped by any commit |
| StepSimulation { ticks } | SimulationResponse { samples, error? } | evaluates ticks; samples carry `DeclId`, active domains, values rendered in design terms |
| ResetSimulation | SimulationResponse | back to tick 0 |
| InitSystemProject { root_path, name } | ProjectResponse | a behaviour-system project; the projection is the derived flat design, `kind = PROJECT_KIND_SYSTEM` |
| GetSystem | SystemResponse { SystemView } | components (with ports, clock parameters, sharing tables and their bodies as projections), instances, bindings, exports, and the origin of every derived flat entity; `system.not_a_system` on a flat project |
| ApplySystemEdit { base_revision, SystemEditOp } | SystemEditApplied { system, project (derived), outcome } | the twenty-one system ops (`docs/BEHAVIOR_SYSTEMS.md`); refused with `edit.stale_revision` or `system_edit.<reason>`; subscribers receive `ProjectChanged` for the derived design |
| RunSystemAnalysis | SystemAnalysisResponse { analysis (flat `ProjectAnalysis`), composition diagnostics, port statuses, acceptance, projected diagnostics } | flatten then `analyze`; every diagnostic carries its origin (instance, local entity, port) |
| ListTargets | TargetsResponse { TargetView { id, display_name, description, family, resource_count, capabilities[] { capability, label, resource_count, shareable } }[] } | the board registry; `id` is opaque, `name` = `display_name` for 0.3 clients |
| AnalyzeDeployment { target_id, revision? } | DeploymentResponse { DeploymentAnalysis } | target-relative; computed afresh per request against the current revision, never cached with the project; `deploy.unknown_target` if the id is unknown; `deploy.stale_revision` if `revision` is given and the project has moved on |
| AnalyzeDefinitionDraft { revision, mapping_id, generation, source } | DefinitionDraftAnalysis { revision, mapping_id, generation, parse_ok, MappingAnalysis } | **read-only**: `source` becomes the mapping's `MappingDefinitionDraft` overlay in the session's `IdeHost`, a snapshot of committed + overlays is composed and `bdl_ide::draft_verdict` answers; no revision, no event, no undo entry, nothing on disk. `draft.stale_revision` if `revision` is not the current one (the client re-asks when its projection arrives), `draft.unknown_mapping` if the mapping does not exist. `generation` is echoed unchanged so the client can drop answers a newer draft superseded. Spans index `source`. Not counted as pending by Studio; debounced 150 ms per mapping (docs/STUDIO_COMPILER_INTEGRATION.md) |
| DiscardDefinitionDraft { mapping_id } | Ack | removes the mapping's draft overlay (revert, reload, detach, or the text returned to the committed definition); idempotent |
| CompleteDefinitionDraft { revision, mapping_id, source, offset } | DraftCompletionResponse { revision, mapping_id, items[] { label, kind, replace_start, replace_end, insert, resulting_type, documentation, relevance } } | sets the overlay to `source`, then `bdl_ide::completion` at the byte `offset`; inputs, units, keywords by the compiler's own name rule; empty is a normal answer |
| HoverDefinitionDraft { revision, mapping_id, source, offset } | DraftHoverResponse { revision, mapping_id, found, span?, concept_id?, entity?, title, representation, signature, status, open, details[], explanation } | the concept named under the byte `offset` (`bdl_ide::entity_at_formula` + `hover`); `found = false` over a number, an operator or whitespace |
| HoverEntity { revision, EntityRef } | DraftHoverResponse (same shape; `entity` echoed, `mapping_id` unused) | the card for a project object by identity — `bdl_ide::hover` over the session's effective snapshot (committed + overlays); `draft.stale_revision` if `revision` is not current, `protocol.missing_field` without an entity; `found = false` for an unknown id |
| ListSemanticActions { revision, EntityRef } | SemanticActionsResponse { revision, entity, actions[] SemanticActionView { id, title, kind, applicability: READY \| NEEDS_CHOICE \| BLOCKED, reason, options[] { label, EditOp }, explanation, edits[] EditOp, addresses[], invalidation } } | `bdl_ide::actions_for` over every diagnostic concerning the entity (`Project` = all) plus `actions_at(entity)`, de-duplicated by id; a READY action carries its edits, which the client applies as ordinary revisioned `ApplyEdit`s; `draft.stale_revision` as above |
| ListConceptTemplates | ConceptTemplatesResponse { libraries[] { id, name, schema_version, version, templates[] { id, display_name, default_name, description, category, role_hint, representation?, type_name, unit, keywords[], icon } }, quantities[] { id, type_name, unit, dim } } | the concept libraries the daemon serves (the Standard Concept Library, `library/std/concepts.toml`) and the shared quantity vocabulary; independent of any project (docs/STANDARD_CONCEPT_LIBRARY.md) |
| InstantiateConceptTemplate { base_revision, template_id, name? } | EditApplied | the one instantiation: the daemon builds `CreateConcept` from the template's defaults with a name free in the project (or `name`) and applies it like `ApplyEdit`; `library.unknown_template`, `edit.stale_revision` |
| Shutdown | Ack | |

`EntityRef` is `project | concept_id | mapping_id | clock_id | output_id |
device_id` — the identity a client names an object by; never a name, never
a text position (docs/IDE_SERVICE_ARCHITECTURE.md).

On a system project `ApplyEdit` is refused with `edit.derived_design`:
the flat design is derived; edit the system (`ApplySystemEdit { Base {
op } }` for the system's own flat design, `EditComponentBody` for a
component). `OpenProject` opens either kind.

`EditOp` covers concepts, mappings, clock domains (`CreateClockDomain`,
`RenameClockDomain`, `DeleteClockDomain`, `SetMappingClock`), outputs
(`CreateOutput`, `RenameOutput`, `SetOutputAccepts`, `SetOutputClock`,
`SetOutputRequired`, `DeleteOutput`, `SetMappingDrive`) and devices
(`CreateDevice`, `RenameDevice`, `SetDeviceKind`, `SetDeviceOutput`,
`SetDevicePin`, `DeleteDevice`); `EditOutcome` reports `created_clock /
created_output / created_device`. Manual pins are deployment constraints
that travel with the device (`SetDevicePin { index, resource? }`) —
there is no separate "manual resource constraint" request.

`DeploymentAnalysis` has two layers. Fields 1–9 are the analysis as
computed, by stable ids: `revision`, `target`, `status: Feasible |
Infeasible | Incomplete`, `requirements[]` (device, index, capability,
fixed?, label), `assignment[]` (device, index, resource), `dead_end?`
(device, index, reason, `placed[]`), `unbound_devices[]`,
`unrealised_outputs[]`, `diagnostics[]` — for tools and the expert view.
Fields 10–15 are the **read model** a Deploy page renders from directly
(docs/DEPLOYMENT_READ_MODEL.md): `target_display_name`, `design_ready`
(semantic + output completeness), `deployable` (`design_ready ∧ status ==
Feasible`), `missing[] MissingItem { kind, output/device/mapping id +
name, message, explanation }`, `rows[] AssignmentRow { output name,
device name + kind label, requirement label, capability label, fixed?,
resource?, resource_label? }`, `blocker? { device, requirement,
capability, kind: no_capable_resource | fixed_unavailable(pin) |
blocked(candidates[] with holder names), message, explanation }`. A
frontend needs no string parsing, no `details_json`, and no knowledge of
what a requirement or a unit relation is.

Planned (ROADMAP): RunSimulation, GenerateRust, Build, Flash, StartTelemetry.

## Errors

`Error { code, message, details_json }`. `code` is stable and
machine-readable (`edit.duplicate_concept_name`, `session.no_project`,
`protocol.invalid_edit`, …); `message` is designer-readable; `details_json`
carries the typed Rust error for the expert view.

## Projection

`ProjectProjection { revision, name, root_path, concepts[], mappings[],
layout, can_undo, can_redo, dirty, clocks[], outputs[], devices[] }` — a
read model for rendering, in deterministic order. `MappingView` carries
`clock_id?` and `drives_output_id?`; `OutputView { accepts, clock_id?,
required }`; `DeviceView { kind, output_id?, fixed_pins[], requirements[]
}` where `requirements` is the kind's requirement table (index, capability,
label) so a pin editor needs no hardware knowledge. `MappingView.state`
carries the paper's workspace state (`declared` / `defined`; the ladder
proper is in `ProjectAnalysis`).

`ProjectAnalysis` adds `outputs[] { id, state: undriven | driven |
ill_formed | conflict, driver?, claimants[] }`, `open_outputs[]` and
`output_complete`.

## Deltas

v0.1 sends the full projection after every commit. Incremental deltas are a
planned, non-breaking addition (a new `ProjectDelta` event); clients must
keep treating `ProjectChanged.project` as authoritative when present.
