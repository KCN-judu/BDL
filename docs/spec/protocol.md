# Studio ↔ bdld protocol

- **Schema**: `crates/bdl-protocol/proto/bdl/v1/bdl.proto` — the single source
  of truth. Rust code is generated at build time (`prost` + `protox`, no
  external `protoc`); Dart code is generated by `just proto` and checked in
  under `apps/studio/lib/protocol/gen/`; CI fails if it drifts.
- **Version**: `PROTOCOL_VERSION` (Rust) / `kClientProtocolVersion` (Dart),
  currently `0.11.0`. Minor versions are additive; equal `major` ⇒ compatible.
  The handshake reports both and a `compatible` flag; Studio refuses to proceed
  on a mismatch. What each minor version added:
  [changes/history/protocol-versions.md](../changes/history/protocol-versions.md).
- **Transport** (v0.1): child-process stdio. A frame is a 4-byte big-endian
  length followed by the protobuf payload, 64 MiB cap. Stdout is the channel;
  bdld logs to stderr. Transport and protocol are separate: loopback TCP can be
  added without touching messages.

## Envelope

```text
ClientMessage { request_id, oneof payload }   →
                                              ←  ServerMessage { Response { request_id, oneof } | Event { oneof } }
```

Exactly one `Response` per request. `Event`s are unsolicited and only sent after
`SubscribeProject`: `ProjectChanged` then `AnalysisReady` for every committed
revision.

`EntityRef` is
`project | concept_id | mapping_id | clock_id | output_id | device_id` — the
identity a client names an object by; never a name, never a text position
(docs/architecture/ide-service.md).

On a system project `ApplyEdit` is refused with `edit.derived_design`: the flat
design is derived; edit the system (`ApplySystemEdit { Base { op } }` for the
system's own flat design, `EditComponentBody` for a component). `OpenProject`
opens either kind. The four draft requests take an optional `component`: the
mapping is then a declaration of that component's body and is judged, completed
and hovered in the body's own scope (a per-body `IdeHost` in the daemon);
`system.unknown_component` otherwise.

`EditOp` covers concepts, mappings, clock domains (`CreateClockDomain`,
`RenameClockDomain`, `DeleteClockDomain`, `SetMappingClock`), outputs
(`CreateOutput`, `RenameOutput`, `SetOutputAccepts`, `SetOutputClock`,
`SetOutputRequired`, `DeleteOutput`, `SetMappingDrive`) and devices
(`CreateDevice`, `RenameDevice`, `SetDeviceKind`, `SetDeviceOutput`,
`SetDevicePin`, `DeleteDevice`); `EditOutcome` reports
`created_clock / created_output / created_device`. Manual pins are deployment
constraints that travel with the device (`SetDevicePin { index, resource? }`) —
there is no separate "manual resource constraint" request.

`DeploymentAnalysis` has two layers. Fields 1–9 are the analysis as computed, by
stable ids: `revision`, `target`, `status: Feasible | Infeasible | Incomplete`,
`requirements[]` (device, index, capability, fixed?, label), `assignment[]`
(device, index, resource), `dead_end?` (device, index, reason, `placed[]`),
`unbound_devices[]`, `unrealised_outputs[]`, `diagnostics[]` — for tools and the
expert view. Fields 10–15 are the **read model** a Deploy page renders from
directly (docs/architecture/deployment-read-model.md): `target_display_name`,
`design_ready` (semantic + output completeness), `deployable`
(`design_ready ∧ status == Feasible`), and three shapes:

```text
missing[] MissingItem { kind, output/device/mapping id + name, message, explanation }
rows[] AssignmentRow { output name, device name + kind label, requirement label, capability label, fixed?, resource?, resource_label? }
blocker? { device, requirement, capability, kind: no_capable_resource | fixed_unavailable(pin) | blocked(candidates[] with holder names), message, explanation }`.
```

A frontend needs no string parsing, no `details_json`, and no knowledge of what
a requirement or a unit relation is.

Not in the protocol yet: build, flash and telemetry requests — they arrive with
roadmap priorities 2–4 (`docs/project/roadmap.md`).

## Errors

`Error { code, message, details_json }`. `code` is stable and machine-readable
(`edit.duplicate_concept_name`, `session.no_project`, `protocol.invalid_edit`,
…); `message` is designer-readable; `details_json` carries the typed Rust error
for the expert view.

## Projection

```text
ProjectProjection { revision, name, root_path, concepts[], mappings[], layout, can_undo, can_redo, dirty, clocks[], outputs[], devices[] }
```

— a read model for rendering, in deterministic order. `ConceptView` carries
`representation?` —

```text
Representation { quantity Dim | boolean | count | optional Representation | list Representation | pair { first, second } }
```

(the structured forms since 0.11) — and `ordered` (the designer declared the
concept ordered, 0.11; `EditOp.set_concept_ordered { id, ordered }` sets it).
`MappingView` carries `clock_id?` and `drives_output_id?`;
`OutputView { accepts, clock_id?, required }`;
`DeviceView { kind, output_id?, fixed_pins[], requirements[] }` where
`requirements` is the kind's requirement table (index, capability, label) so a
pin editor needs no hardware knowledge. `MappingView.state` carries the paper's
workspace state (`declared` / `defined`; the ladder proper is in
`ProjectAnalysis`).

`ProjectAnalysis` adds
`outputs[] { id, state: undriven | driven | ill_formed | conflict, driver?, claimants[] }`,
`open_outputs[]` and `output_complete`.

## Values

```text
Value { boolean | count | quantity { dim, value } | semantic { concept_id, repr } | none | some | opaque
      | list { items[] } | pair { fst, snd } }
```

is the reference evaluator's value in every simulation message; `list` and
`pair` (0.11) carry collections and grouped values in the list's own order.
`opaque` is shown and never supplied.

## Deltas

Every version so far sends the full projection after every commit. Incremental
deltas would be an additive change (a new `ProjectDelta` event) and are an open
design issue (ISS-0009); clients must keep treating `ProjectChanged.project` as
authoritative when present.
